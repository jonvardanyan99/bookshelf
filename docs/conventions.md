# Conventions

Reusable rules for a Next.js (App Router) + React + TypeScript + Tailwind v4 project. Keep this file free of project-specific names and facts: those live in the project's `CLAUDE.md`, which imports this file. See [Adding rules](#adding-rules) at the end.

To reuse in another project, copy this file together with what the rules depend on: `eslint.config.mjs`, `.prettierrc`, `.husky/`, the CI workflow, and the `Typography` and `Button` components. Then write a `CLAUDE.md` with that project's facts (stack, commands, API, architecture, design tokens, shared components, z-index order) and `@docs/conventions.md` at the top.

## Approach

- **Docs first:** always refer to the latest docs of a library when the task depends on how it works (APIs, options, caching, routing, configuration), instead of relying on memory: libraries change and memory is often outdated. Use the docs for the installed version: for Next.js, the bundled guides `AGENTS.md` points to; for other libraries, their official docs or the docs shipped in `node_modules`.
- **Simplest setup first:** start from the plain setup the official docs show. Add layers such as CSS variables, theme indirection, base-layer rules or extra fonts only when a current need requires them, not for possible future ones.
- **Keep scaffold code:** leave the code generated by the project's starter (`create-next-app` and similar) as it is, including its config blocks, template comments and default README. Adding new options to those files when a feature needs them is fine; rewriting, "cleaning up" or removing their own lines is not.

## Tooling

Verify every change with `npm run type-check` and `npm run lint`.

Git hooks (Husky): pre-commit runs lint-staged (`eslint --fix` on staged TS, `prettier --write` on CSS/JSON/MD) plus `type-check`; pre-push runs `lint`, `format` and `type-check`. CI (`.github/workflows/ci.yml`) runs the same three. Never bypass the hooks with `--no-verify`.

ESLint is extremely strict (`js.configs.all`, `strictTypeChecked`, `react.configs.all` on top of `eslint-config-next`). Rules that shape the code most:

- **`sort-keys`** — object literal keys and JSX props are alphabetical, ignoring case (this is why code looks sorted); `perfectionist` does the same for interfaces, object types and destructured props. Opt out per file only where order matters (`/* eslint-disable sort-keys */`).
- **`import/no-default-export`** — named exports only, except Next.js route files (`page`, `layout`, `template`, `loading`, `error`, `global-error`, `not-found`, `default`, `forbidden`, `unauthorized`), metadata files (`sitemap`, `robots`, `manifest`, `icon`, `apple-icon`, `opengraph-image`, `twitter-image`) and root `*.config` files, which Next requires to default-export. Imports auto-sorted by `simple-import-sort`.
- `max-lines` 350 per file/function — split components rather than disabling.
- `react/forbid-component-props` / `react/forbid-dom-props: style` — no `style` prop on components or HTML elements; use Tailwind classes.
- `react/jsx-no-bind` — only arrow functions inline; prefer `useCallback` handlers.
- `@typescript-eslint/no-empty-function` — a handler that isn't built yet contains only `// Not implemented yet`.
- Prettier: 100 cols, single quotes, tailwind class sorting. It runs inside ESLint (`prettier/prettier`), so formatting issues fail `npm run lint` and `lint:fix` fixes them.

## Architecture

```
src/
├── app/          # App Router: layout.tsx, page.tsx, globals.css (Tailwind + theme tokens)
├── components/   # Shared UI (Typography, Button and other components rendered from more than one place)
├── constants/    # App-wide constants (routes.ts)
└── services/     # API calls and their types
```

- **Routes:** every internal path comes from `ROUTES` in `src/constants/routes.ts` (`href={ROUTES.home}`), never a hardcoded string. A new page adds its path there first.

- **Services:** every API call lives in `src/services/` as a function cached with `'use cache'` + `cacheLife`, with its types next to it. Only call endpoints that exist in the API's official docs.

Components nest under their owner: `Page/components/Child/components/Grandchild/index.tsx`. Route files own the `components/` folder next to them (`app/components/` for `layout.tsx` and `page.tsx`). Promote to `src/components/` only when rendered from more than one place; a component rendered once stays under its owner, even when its owner is a layout that every page shares (a site header or footer).

- **Server first:** components are Server Components; put `'use client'` on the smallest interactive part (a button, an input), not on its parent. The static structure around it (landmarks, `ul`/`li`, headings, links) stays in the server parent, and server content goes into a client child as `children`. A component whose whole job is interaction (a modal, a form with state) is a client component as a whole. Otherwise keep a component's markup in its own file and extract a child only when it must be client or its logic grows.

- **Imports:** always the `@/…` alias (→ `src/`) instead of long relative paths. Use `import type` for types.

## Code conventions

- Interfaces, not `type`, for object shapes (API types, Props); `type` for unions/derived types.
- Never write a union inline in a signature (`size: 'L' | 'M' | 'S'`): declare a named top-level `type` (`type IconSize = …`) and use it.
- Nested object types put one property per line, even when there's only one: write `roles` in `GetUserResponse` as a multi-line `{ … }[]`, never inline as `{ name: string }[]`. Prettier keeps them expanded.
- Service types are named after their function: `getUser` takes `GetUserVariables` and returns `GetUserResponse` (`Variables`, not `Params`). Services own their defaults (`limit = 10`); never build request values from UI constants such as class-name arrays.
- Unused vars/args must be prefixed `_`.
- **Minimal comments:** no comments that justify a choice or label a section (`// Relaxed: conflicts with…`, `/* Colors */`); blank lines separate sections. Comment only where the code would genuinely surprise a reader, such as a non-obvious constraint.

### Component idiom

Nearly every component is a private `Component` wrapped in `memo` and exported by name:

```tsx
interface Props {
  onClose: () => void;
}

const Component: React.FC<Props> = ({ onClose }) => { ... };

export const MyModal = memo(Component);
```

Route files (`page.tsx`, `layout.tsx`) are the exception: they default-export a function as Next.js expects.

- Name components (and their folders) after what they show or do, usually matching their heading or `aria-label` (`ProductReviews`, `PricingPlans`, `UserAvatar`). Never use layout or position words (`HomeRow`, `TopSection`, `LeftColumn`) or vague ones (`Wrapper`, `Content`, `Block`). The same goes for data constants and their properties: name them after what the data is (`LINK_GROUPS` with `links`, `PRICING_PLANS`), not how it's laid out (`COLUMNS`, `ROWS`) or a generic word (`ITEMS`, `DATA`).
- Modal visibility lives in the parent: `const [xModalVisible, setXModalVisible] = useState(false)` with `showXModal` / `hideXModal` callbacks.
- Multi-step flows = separate modals per step, wired with `onNextClick` / `onBackClick` from the parent.
- Render optional JSX with `&&` (`{product.badge && <Badge … />}`), not a ternary ending in `: null`; use a ternary only when both branches render something. Coerce a number on the left (`products.length > 0 &&`) so `0` isn't rendered.
- Prefer a named boolean (`const hasResults = …`) over complex inline JSX conditions; inline single-use expressions and single-use class strings; use a `*_CLASS_NAME` constant only when reused in the file.
- Use concise `map((x) => (<…/>))` unless logic precedes the return. Array callbacks (`map`, `filter`, `find`…) take the whole item, named as the singular of the array (`products.map((product) => …)`, then `product.name`), and never destructure it in the parameter (`({ name, price }) =>`).
- List keys come from the data (`key={item.id}`), never from class names or array indexes. Map over the data itself, not over a styling array.
- Reuse types via indexed access (`GetUserResponse['roles']`) rather than new aliases.
- Verify exported names (constants, helpers, response shapes) before using them — don't guess.

## Styling

Tailwind v4 — config lives in the global stylesheet's `@theme`, no tailwind.config. Keep the design tokens (colors, then type) together at the top of `@theme`. Don't mix anything else in with them: other values such as `--shadow-*` go at the end of the block, after a blank line. The project's tokens are listed in `CLAUDE.md`; prefer them over Tailwind's default palette.

- **Font:** one font from `next/font`, applied once via its `className` on `<html>` in `layout.tsx` — never set a font family on components.
- **Typography:** use `<Typography variant="…">` from `@/components/Typography` — it renders the matching element and `text-<variant>` utility, and makes headings bold. Each `--text-<variant>` token is a px size with its own line height (`--text-<variant>--line-height`). Use these tokens instead of arbitrary font sizes. `variant` decides the element; to change its size or weight, add a utility in `className` — there is no `component` prop. Use `!` exactly when the class overrides a property the variant already sets: every size (`<Typography className="text-h4!" variant="h2">`) and a heading's weight (`font-medium!` on an `h2`). Then always use it, even where the override seems to work without it: Tailwind v4 breaks ties between same-property utilities by class name order, so a plain override wins only by accident, and renaming or adding a token can silently flip it. Where nothing competes, `!` does nothing, so leave it out (`font-semibold` on a `body` or `caption`, which set no weight). Don't add tailwind-merge for this. All text goes through Typography, never bare `span`/`p` (not even as empty or decorative boxes: use `div`); inline text inside a paragraph or button uses `variant="caption"` (a `span`) with a size override.
- **Buttons:** every button is `<Button variant="…">` from `@/components/Button`, never a bare `<button>`. The variant owns the look, and Button adds the shared classes (cursor, radius), a default size (height, horizontal padding and text size; the values are in the project's `CLAUDE.md`), `whitespace-nowrap` (a fixed-height button holds one line; a wrapped label overflows it and shifts its baseline) and `type="button"`. The caller passes layout, the sizes that differ from the default as `!` overrides (`h-[32px]! text-subtitle!`, by the same `!` rule as Typography), and extras that only its placement needs and the variant doesn't set (`shadow-raised` on a button that sits on a card). It never re-adds or changes the colors, borders or radius the variant owns: a new look shared by several buttons becomes a new variant in Button. Button is a Client Component and `onClick` is required (a button without one isn't a button): a `useCallback` handler in a `'use client'` component. A Server Component (static or async data-fetching) can't pass functions, so its button becomes a client child under its `components/` folder (see **Server first**): `SubscribeButton`, or `ProductCardButton` taking server-rendered `children`.
- **Shadows:** only `--shadow-*` tokens, never an arbitrary `shadow-[…]`: add a token instead.
- **Images:** size `next/image` with classes, not `width`/`height` props. Put the size classes on the image itself and let its parent follow its content (`<Image className="size-[40px]" src={logo} … />` from a static import). Only a remote image, which has no intrinsic size, takes `fill` and `sizes` inside a positioned parent that holds the size classes. `alt` always describes the image (for example the product name), never `""`, even when text beside it repeats the name (a logo next to the site name gets `alt="Acme logo"`). Remote image hosts must be in `images.remotePatterns` in `next.config.ts`.
- Check tokens before using arbitrary values; add a token when a value is semantic or repeated 3+ times.
- Use the simplest classes that give the result: a fixed size (`w-[120px] shrink-0`) rather than `calc()` formulas repeated per breakpoint, or `min-w-*` on items that never grow. Let a box's height come from its content plus padding (`p-[24px_8px]`) rather than an arbitrary `h-*`/`min-h-*`. Never size both a box and the content that already gives it that size (an `h-*` on a link around a sized logo): the content decides, and the box follows. To make a container taller or shorter (a header, a bar), change its top and bottom padding, never a child's size or margin. A box whose children can't size it (only absolutely positioned layers) takes a fixed size. Buttons are the exception: they take a fixed `h-*` so same-size buttons stay equal without tuning vertical padding in each caller. Add responsive variants only when the design needs them.
- No defensive classes: every class must visibly change the result with the content the component actually renders. Don't add `min-w-0`, `shrink-0`, `whitespace-nowrap`, `text-balance`, `w-full`, `justify-*` and similar "just in case". Add one when real content needs it (a long unbreakable string, a scroll row of fixed-width items). If removing a class changes nothing in the browser at any width, delete it.
- Arbitrary pixel values are the norm for spacing and sizes (`mb-[24px]`, `p-[24px_32px]`, `size-[18px]`, `max-w-[340px]`). Always `px`, never `ch`, `em` or `rem` (no `max-w-[18ch]`); `%` only for proportions such as a flex basis. No negative spacing values. Shorthands take 2 or 4 values, never 3 (`p-[0_20px_20px_20px]`, not `p-[0_20px_20px]`), and never override a shorthand with a side class (`p-[4px] pr-0`): write the 4-value form instead. Opposite sides get equal padding (`p-[24px]`, `p-[24px_16px]`), so the 4-value form appears only where the design really needs unequal sides.
- Conditional classes via `clsx`, imported by name: `import { clsx } from 'clsx'`. Argument order: variable class names first (`SIZE_CLASS_NAMES[size]`, a `className` prop), then the static class string, then conditional objects (`{ 'opacity-50': disabled }`).
- Elements:
  - Landmarks: `<main>` (rendered once in `layout.tsx` around `{children}`, so pages never add their own), `<header>`, `<nav>` (`aria-label` when there is more than one), `<footer>`, `<aside>` (sidebars like filters), `<search>` (wraps a search form).
  - Always the real element when it does something or gives structure: `button`, `a`/`Link`, `form`/`label`/`input`/`select`/`textarea`, `fieldset`/`legend`, `h1`–`h6` in order (one `h1` per page), `img` with `alt`, `table`/`th` (data only), `dialog`, `details`/`summary`. Optional: `time`, `blockquote`, `figure`/`figcaption`.
  - `ul`/`ol`/`li` only where it's really necessary: a set of items of the same kind, usually mapped from data, where hearing "list, N items" helps (blog posts, cards, tiles, nav and footer link groups). Everything else is `div`s, including a couple of unrelated controls such as Log In / Sign Up. A bulleted list of facts in prose is `<ul className="mb-[24px] flex list-disc flex-col gap-[12px] pl-[24px]">` / `<li>`.
  - `dl`/`dt`/`dd` for name–value pairs that describe one subject (product specs, stats, a product's key features), so screen readers tie each value to its name. Separate items that each have a title and a description (cards, posts) stay a `ul`. Wrap each pair in a `div` (`key` from the data) for layout. `dt` always comes before `dd` in the markup: when the value shows first (a stat number above its label), reverse it visually with `flex-col-reverse`. A reversed column packs its content to the bottom, so when pairs of different heights share a row, add `items-start` on the parent to keep them top-aligned.
  - Every component returns a semantic root element, never a bare `div` or a fragment (route files may return a fragment). The exception is a component that is just a layout group with no fitting element (a pair of buttons), which uses a `div`. A page block is `<section aria-labelledby="…">` pointing at its heading's `id` (Typography takes `id`), with the id in a `const TITLE_ID = '…-title'` used in both places; a block without its own heading uses `aria-label`.
  - `div` only for layout inside those elements, and only when an existing element can't take the layout itself. Before wrapping children in a `div`, put the classes on their parent instead (`flex flex-col justify-center` on the card rather than an inner `div` to stack its texts, the parent's padding rather than a `div` with a margin). No `<article>`.
- Vertical margins flow top to bottom: each element sets `mb-*` for the gap below it; never `mt-*` or `my-*`. The one exception is an optical alignment nudge: a column whose smaller text should line up with a larger heading beside it moves down with `mt-*`, never `pt-*`. Add a nudge only when the element visibly misaligns without it, never by default or copied from another site, and never to change its container's height. The gap at the top of a container is its own top padding. The gap below a component goes on its root element, never on its last child. The last element in a container gets no bottom margin: the space below it is the container's bottom padding.
- **Consistency:** the same relationship always gets the same styling across the codebase: spacing, sizes, widths, colors, radius, type, scrollbars. Before picking a value, find how existing components handle the same case and reuse it; never introduce a one-off value. If the right value differs from an existing one, change it everywhere. Spacing between texts follows the project's text spacing scale in `CLAUDE.md` (measure the visible gap, including a scroll row's shadow padding).
- **No repeated layout fixes:** when several components need the same layout fix (page width `mx-auto max-w-[…]`, a shared inset), put it once in the shared parent, usually `layout.tsx`, instead of repeating it in each component.
- Space between sibling elements is `gap` on their flex container, never padding on one of the siblings. Repeated siblings (mapped list items, wrapping columns) always get one `gap` on the parent (`flex flex-col gap-[12px]`), never `mb-*` on each child with `last:mb-0`. `mb-*` in plain block flow is only for a few distinct stacked elements (a heading, then a paragraph), which don't need a flex+gap wrapper. Padding is only for the inset between a box and its own content. Prefer plain `gap-[…]`, as the rest of the codebase does, even in a wrapping row where wrapped items then get the same gap. Use `gap-x-*`/`gap-y-*` only when the design really needs different gaps on the two axes.
- Layout with flexbox; use grid only when flex can't do it simply: genuinely two-dimensional layouts, such as N equal columns that wrap into rows, which flex could only do with a `calc()` basis that repeats the gap (`basis-[calc((100%-12px)/2)]`, use `grid grid-cols-2` instead). Absolute positioning only for overlays/floating decorations.
- z-index values are consecutive integers (`z-1`, `z-2`, `z-3`), one per stacking layer, never large or arbitrary numbers (`z-10`, `z-50`, `z-[999]`). A new layer takes the next number, or goes between existing ones and the numbers above it shift up. The current order is listed in `CLAUDE.md`; keep it up to date.

## Implementing designs

- Match the design exactly (size, spacing, colors, type, radius, shadows); never guess values.
- Icons: use the real exported SVG (kebab-case file name) rendered with `next/image` or `<img alt="…" />`. Never placeholders, emoji, or icon libraries (lucide, react-icons).

## Adding rules

When the user asks for a new rule or points out something that should be one:

1. **Generalize it:** write the principle behind the case ("no defensive classes", not "don't use `min-w-0` in the stats card"), with the reason when it isn't obvious.
2. **Place it** by asking whether it would still make sense in a different project:
   - Yes → this file, with a neutral example (`ProductCard`, never a component name from the current project).
   - No, it's about this project (a color, its API, its z-index order) → `CLAUDE.md`.
   - Both (a general rule with project values, like a spacing scale) → the rule here, the values in `CLAUDE.md`.
   - Unclear (a decision such as "light theme only") → ask "this project only, or all projects?" before writing it.
   - Never in Claude's memory: memory is per project and doesn't travel. It holds only facts about the user or project that no file records.
3. **Check existing rules:** extend a rule it overlaps instead of adding a near-copy; if it contradicts one, ask which wins.
4. **Apply it:** find code that already breaks the new rule and fix it.
5. **Enforce it:** add a lint rule only when the user asks for one; don't suggest one with every new rule.
6. **Report** in the reply which file the rule went into, so the user can correct the placement.
