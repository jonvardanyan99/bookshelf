# Conventions

Reusable rules for a Next.js (App Router) + React + TypeScript + Tailwind v4 project. Keep this file free of project-specific names and facts: those live in the project's `CLAUDE.md`, which imports this file. See [Adding rules](#adding-rules) at the end.

To reuse in another project, copy this file together with what the rules depend on: `eslint.config.mjs`, `.prettierrc`, `.husky/`, the CI workflow, and the `Typography`, `Button` and `Link` components. Then write a `CLAUDE.md` with that project's facts (stack, commands, API, architecture, design tokens, shared components, z-index order) and `@docs/conventions.md` at the top.

## Approach

- **Docs first:** always refer to the latest docs of a library when the task depends on how it works (APIs, options, caching, routing, configuration), instead of relying on memory: libraries change and memory is often outdated. Use the docs for the installed version: for Next.js, the bundled guides `AGENTS.md` points to; for other libraries, their official docs or the docs shipped in `node_modules`.
- **Simplest setup first:** start from the plain setup the official docs show. Add layers such as CSS variables, theme indirection, base-layer rules or extra fonts only when a current need requires them, not for possible future ones.
- **Accessibility fixes:** add small accessibility improvements (screen reader announcements and similar) as part of the work and mention them in the summary, instead of offering them and waiting for approval. Ask first only when one would change the visible design or a product decision.
- **Keep scaffold code:** leave the code generated by the project's starter (`create-next-app` and similar) as it is, including its config blocks, template comments and default README. Adding new options to those files when a feature needs them is fine; rewriting, "cleaning up" or removing their own lines is not.

## Tooling

Verify every change with `npm run type-check` and `npm run lint`.

**Verify behavior, not just types:** before calling a change done, run it in the app, both the main flow and the ways it can break: wrong or odd input (casing, spaces, too long), repeated or concurrent submits, a second tab, missing or stale state (a deleted record, an expired cookie, an unset env var).

**Heavy testing:** when asked to test thoroughly, or before calling a feature that writes data or handles sessions done:

- **Real app, isolated data:** run a production build on its own port, with a throwaway database and secrets set in the process env, which take priority over env files. Never test against the real database, and compare its hash before and after to prove it didn't change.
- **Nothing new installed:** use the runtime and the project's own dependencies, unless the user asks for a test tool. Submit forms in the same request format the browser uses, including the framework's own encoder where it has one.
- **Try to break it:** besides the cases above, cover forged, tampered and expired tokens, cross-origin requests, parallel submits, corrupted records, a database with missing tables, and each external API failing, never answering and then recovering, using a small local stub.
- **Prove the test first:** when a check fails or passes unexpectedly, confirm the test itself is valid (the stub received requests, the text is in the visible HTML and not only in script data) before reporting a result. After a fix, rerun the same checks.
- **Report honestly:** separate confirmed bugs from plausible ones, list ruled-out suspects, and list what couldn't be tested (anything needing a browser) as untested, never as passed.
- **Clean up:** stop only the processes you started, never a dev server already running, delete the temp data, restore a working build, and confirm `git status` shows nothing unexpected.

Git hooks (Husky): pre-commit runs lint-staged (`eslint --fix` on staged TS, `prettier --write` on CSS/JSON/MD) plus `type-check`; pre-push runs `lint`, `format` and `type-check`. CI (`.github/workflows/ci.yml`) runs the same three plus `build`. Never bypass the hooks with `--no-verify`.

Claude Code hooks (`.claude/settings.json`, scripts in `.claude/hooks/`): when Claude finishes a turn, the user gets a desktop notification with the first line of Claude's last message, so they know the work or test is done without watching the terminal. Hooks for the same event run in parallel, so the notification is sent by the stop hook that runs the end-of-turn checks, and only when those checks pass: a separate notification hook would fire even when a failed check sends Claude back to work.

ESLint is extremely strict (`js.configs.all`, `strictTypeChecked`, `react.configs.all` on top of `eslint-config-next`). Rules that shape the code most:

- **`sort-keys`** — object literal keys and JSX props are alphabetical, ignoring case (this is why code looks sorted); `perfectionist` does the same for interfaces, object types and destructured props. Opt out per file only where order matters (`/* eslint-disable sort-keys */`).
- **`import/no-default-export`** — named exports only, except Next.js route files (`page`, `layout`, `template`, `loading`, `error`, `global-error`, `not-found`, `default`, `forbidden`, `unauthorized`), metadata files (`sitemap`, `robots`, `manifest`, `icon`, `apple-icon`, `opengraph-image`, `twitter-image`) and root `*.config` files, which Next requires to default-export. Imports auto-sorted by `simple-import-sort`.
- `max-lines` 350 per file/function — split components rather than disabling.
- `react/forbid-component-props` / `react/forbid-dom-props: style` — no `style` prop on components or HTML elements; use Tailwind classes.
- `react/jsx-no-bind` — only arrow functions inline; prefer `useCallback` handlers.
- `@typescript-eslint/no-empty-function` — a handler that isn't built yet contains only `// Not implemented yet`.
- Prettier: 100 cols, single quotes, tailwind class sorting. It runs inside ESLint (`prettier/prettier`), so formatting issues fail `npm run lint` and `lint:fix` fixes them.

## Architecture

```
src/
├── app/          # App Router: layout.tsx, page.tsx, globals.css (Tailwind + theme tokens)
├── actions/      # Server Actions, one file per domain (auth.ts)
├── assets/       # Static images imported by components (icons/success-circle.svg)
├── components/   # Shared UI (Typography, Button and other components rendered from more than one place)
├── constants/    # App-wide constants (routes.ts, cookies.ts)
├── db/           # Database client and schema
├── hooks/        # Client hooks shared by several components (useFormAction.ts)
├── lib/          # Server-only code: session cookie, data access layer, toast cookie
├── services/     # API calls and their types
├── types/        # Shared interfaces (models.ts) and form state types (formValues.ts)
└── utils/        # Form schemas (formSchemas.ts) and other helpers
```

- **Mutations:** every write is a Server Action (`'use server'` file in `src/actions/`) called from a `<form action={…}>`, through the shared `useFormAction` hook (`useActionState` on the action itself, so the form still submits without JavaScript) in a client form for its returned errors. A form that needs no returned state (a log out button) passes the action straight to `action` from a Server Component. An action is a public endpoint: it validates its input with a schema on the server and returns field errors and the values to refill (never passwords), plus a form-level message only when its failure isn't about one field (a failed login), and checks the session itself when it needs a user. Actions share one form-parsing helper (read the fields, validate, collect field errors and refill values) instead of repeating those steps, and their user-facing messages live in one `ERROR_MESSAGES` constant next to the schemas in `src/utils/formSchemas.ts`. Toast messages live in `src/constants/toasts.ts`, even one used by a single module, in two constants: `TOAST_SUCCESS_MESSAGES`, a list of `{ message, name }` for the success toasts whose names a toast cookie holds (`loggedIn`), and `TOAST_ERROR_MESSAGES`, an object for the error toasts, keyed by the error each one names (`unexpected`, `connectionLost`), so the app's user-facing messages are in exactly these two files. A message for a schema check is named after that check, so it reads the same as the validator it's passed to (`.min(8, { error: ERROR_MESSAGES.min(8) })`); any other message names the error (`emailTaken`). Each form has its own state type in `src/types/formValues.ts`, built on a shared base of errors and values and adding only what its action returns (a log-in state adds `message`), so a form can only render what its action can send. Every key is optional, so the form starts `useActionState` with `{}`. Server-only modules start with `import 'server-only'`.
- **Feedback:** the user always sees when something is loading and how an action ended, and feedback appears only where there's something to report.
  - **Loading:** use the shared `Loader` component where the user actually waits. It centers its spinner in its own box, so a caller places and sizes it with `className` instead of wrapping it in a `div`. The box is the spinner plus padding, never a fixed `h-*`/`w-*` on top of the spinner's `size`: the padding is the length to reserve minus the spinner size, split equally between opposite sides. A submit button shows it by itself (`useFormStatus`), and a `<Suspense>` around content that streams in and takes up space gets it as a `fallback` sized like that content (`<Loader className="px-[76px]" />` reserves 168px around a 16px spinner), so nothing shifts when the content arrives (never the real content as a guess, such as Log In links for a user who may be logged in). A static or prefetched page needs no `loading.tsx`.
  - **Empty results:** a fetch that succeeds with nothing in it (a search with no matches) is a normal outcome, not an error: the component returns the shared `EmptyData` component early, where the list would have been (`if (productsResponse.products.length === 0) return <EmptyData />`), never an empty list and never a toast. Data that is only decorative and hidden from screen readers (the images of a link card) needs no empty state.
  - **Toasts:** a successful action and an error that isn't about the form's input show a toast: a server failure, a lost connection, an external API being down. A failure never takes the user to another page. Errors about the input (a taken email, a failed login) stay inline in the form, where they remain visible while the user fixes them, with `role="alert"` so screen readers announce them. `error.tsx` is only for a page that can't render at all.
  - **Imperative calls:** client code shows a toast by calling the toast library's `toast.success(message)` or `toast.error(message)`, never by rendering a toast component. A form's hook calls it in an effect when the action's returned state carries a toast message. One toaster in the layout renders every toast, unstyled and given the design tokens and the project's own icons, so several toasts stack and a toast stays until its timer or the user dismisses it, across navigations and redirects. A toast that can be requested more than once at the same time (development's double effect, several components reporting the same outage) passes its message as the toast `id`, so a repeat updates the shown toast instead of adding another. Toasts live in the browser: never call `toast` on the server.
  - **The server decides the message:** the server picks every message and hands it to the client as data. An action that stays on the page returns its toast message in the form state (`toastError`), and the form's hook shows it. An action that redirects sets a short-lived toast cookie just before it, which a Server Component in the layout reads. A Server Component that detects a problem (an external API down) or reads that cookie renders the shared client component that shows a toast from its `message` and `type` props, passing the cookie's name when the toast came from one so the component deletes it. Its effect calls `toast` without dismissing it in a cleanup, so the toast survives the component unmounting. The toast shows every time the component renders, with or without a cookie: its message as the toast `id` already merges the same toast requested at the same time. Never remember which messages were shown to skip them later, since a generic message would then hide later, separate failures (the same outage in a section opened afterwards, or a new outage after a recovery). A new case passes its own message to that component instead of adding another client component that shows a toast. A component that fetches returns that toast early when the data is missing (`if (!productsResponse) return <ServerToast … />`), never rendering it beside its content. When the data feeds only part of a component that must render anyway (the images of a link card, whose link and name don't depend on the fetch), that part becomes its own fetching child, and the parent doesn't fetch. An action never sets a cookie without redirecting: that refreshes the page, which remounts the form and loses its returned values. `redirect` goes outside the action's `try`.
  - **Lost connection:** never wrap the action in a client function to catch a rejected call: that drops the form's no-JavaScript submit. A rejected form action reaches the nearest error boundary, so every form sits inside the shared form boundary (built with the framework's `catchError`, which lets redirects through). The boundary shows an error toast, saying the connection was lost when the browser is offline and the generic error otherwise, then remounts the form. The case is rare, so the form starts empty rather than adding code to refill it.
- **Request reads:** a component that reads request data (cookies, the current user, a page's `searchParams` or `params`) is an async Server Component rendered inside `<Suspense>` by its parent, so the rest of the page stays in the static shell. Read the user through the data access layer, which returns only the fields the UI needs. A page never awaits its `searchParams`/`params`: it passes the promise to the section that needs it, where one async component inside `<Suspense>` awaits it and passes plain values (`category: Category`, never `Promise<Category>`) to its children. Never add a parallel route or a layout just to give a section its own `searchParams`.

- **Routes:** every internal path comes from `ROUTES` in `src/constants/routes.ts` (`href={ROUTES.home}`), never a hardcoded string. A new page adds its path there first. A proxy has no `matcher` (the framework reads it at build time without running the code and silently ignores variables): it runs on every request and checks `request.nextUrl.pathname` against `ROUTES` itself.
- **Shared constants:** a constant used by more than one module (a cookie name, a storage key) lives in `src/constants/`, in a file named after what it holds (`cookies.ts`), and every module imports it from there, never from another module that happens to use it (`import { SESSION_COOKIE } from '@/constants/cookies'`, not from `@/lib/session`). A constant used by one module stays in that module. A constant that gets its own file (a large data list, such as a product catalog's categories) goes in `src/constants/` too, even with a single user (`src/constants/categories.ts`), never in a file beside a component.

- **Services:** every API call lives in `src/services/` as a function, with its types next to it. Each API has its own folder, whose `index.ts` is the shared request helper, and its endpoints are grouped by domain in subfolders with `index.ts` and `types.ts` (`services/shopApi/index.ts`, `services/shopApi/products/index.ts`). Every call goes through that one shared request helper, which owns the base URL, headers, timeout, the failed-response check and caching; a service passes only its path and params and returns the helper's result. The helper uses the native `fetch`, never an HTTP client library (Axios, ky): the framework's caching works the same with any client, so a library only adds a dependency for what `fetch` does in a few lines (`new URL` for the base URL, `URLSearchParams` for the query, `AbortSignal.timeout` for the timeout, and a `response.ok` check, since `fetch` doesn't reject on an error status). The helper is cached with `'use cache'` + `cacheLife` (its arguments are the cache key, so each request is cached separately), and when the pages using an API can render without its data, it catches the failure inside the `'use cache'` scope and returns `null` with a short `cacheLife`: an error that leaves the scope fails the prerender even when the caller catches it, the short lifetime lets the page recover on its own, and `null` lets the page tell an outage from a real empty result and show a toast. Response types describe the API's real response, never widened to fit the failure. Only call endpoints that exist in the API's official docs.

Components nest under their owner: `Page/components/Child/components/Grandchild/index.tsx`. Route files own the `components/` folder next to them (`app/components/` for `layout.tsx` and `page.tsx`). Promote to `src/components/` only when rendered from more than one place; a component rendered once stays under its owner, even when its owner is a layout that every page shares (a site header or footer).

- **Server first:** components are Server Components; put `'use client'` on the smallest interactive part (a button, an input), not on its parent. The static structure around it (landmarks, `ul`/`li`, headings, links) stays in the server parent, and server content goes into a client child as `children`. A component whose whole job is interaction (a modal, a form with state) is a client component as a whole. Otherwise keep a component's markup in its own file and extract a child only when it must be client or its logic grows.

- **Imports:** always the `@/…` alias (→ `src/`) instead of long relative paths. Use `import type` for types.

## Code conventions

- Interfaces, not `type`, for object shapes (API types, Props); `type` for unions/derived types.
- Never write a union inline in a signature (`size: 'L' | 'M' | 'S'`): declare a named top-level `type` (`type IconSize = …`) and use it.
- Nested object types put one property per line, even when there's only one: write `roles` in `GetUserResponse` as a multi-line `{ … }[]`, never inline as `{ name: string }[]`. Prettier keeps them expanded.
- An interface used across modules (a shared helper's return shape) lives in `src/types/models.ts` and is imported from there (`import type { PaginatedList } from '@/types/models'`). A service's types stay next to it and a component's `Props` stay in its file.
- Service types are named after their function: `getUser` takes `GetUserVariables` and returns `GetUserResponse` (`Variables`, not `Params`). Services own their defaults (`limit = 10`); never build request values from UI constants such as class-name arrays.
- **Let TypeScript infer:** don't annotate a variable, return type, callback parameter or generic argument when inference already gives the right type (`const total = price * quantity`, not `const total: number = …`; `useState(false)`, not `useState<boolean>(false)`). Annotate only where inference gets it wrong or the annotation is a contract the value must meet: a tuple TypeScript would widen to an array (`map((name): [string, string] => …)`), a function whose callers need one declared shape rather than the union of its returns (an action returning `Promise<CheckoutFormState>`), an empty value whose type can't be inferred (`useState<Product | null>(null)`), an object checked against a framework or exhaustive type (`metadata: Metadata`, `Record<Variant, string>`), and a literal written to join data of a declared type, such as a list that adds a literal item to typed items (`const categories: Shop['categories'] = [{ name: 'All', slug: 'all' }, ...shop.categories]`), so the literal is checked against that type instead of widening the inferred one. A function with two kinds of result (success or failure) always returns the same declared shape, with only the values changing (`{ data: null, errors, values }` or `{ data, errors: {}, values }`). The caller checks a value (`if (!result.data)`), never a property's presence (`'errors' in result`) or a flag such as `success: false` plus `as const` added only so TypeScript can narrow.
- Adapt the code to a value's type rather than changing the type to fit the code. When a precise type (an `as const` object's literal values) doesn't fit a call (`STATUSES.includes(value)` rejects a plain `string` `value`), write the code so it fits (`STATUSES.some((status) => status === value)`) instead of widening the type with an annotation (`: string[]`) or a cast (`as`). Asserting a type is only for a value that has none (`any` or `unknown`, such as `response.json()`).
- **Descriptive names:** every name (function, variable, parameter, constant) says what the thing is or does, so a reader understands it without opening its definition: `getFieldValue(formData, 'email')`, not `getText`; `derivedKey` beside `storedKey`, not `key`; `isExpired`, not `flag`. Avoid generic words (`data`, `info`, `item`, `temp`, `helper`) unless the context makes them exact (`result` of a `safeParse`). Components and data constants follow the naming rule in **Component idiom**.
- **Write it once:** when several files would repeat the same value or code, put it once in the place they share and let each file add only what differs: the site name in the root layout's `title.template` (`'%s | Acme'`), with each page's `metadata` setting only `title: 'Pricing'`. Layout fixes follow the same rule (see **No repeated layout fixes**). This doesn't apply to small markup: a few lines that render one shared component with its props (an error message as a `Typography` with `role="alert"`) stay inline in each file, since a component wrapping them adds a file and an indirection without saving anything.
- Unused vars/args must be prefixed `_`.
- **Minimal comments:** no comments that justify a choice or label a section (`// Relaxed: conflicts with…`, `/* Colors */`); blank lines separate sections. Comment only where the code would genuinely surprise a reader, such as a non-obvious constraint.

### Component idiom

Nearly every component is a private `Component` wrapped in `memo` and exported by name:

```tsx
interface Props {
  onClose: () => void;
}

const Component: React.FC<Props> = ({ onClose }) => { ... };

export const MyModal = memo(Component);
```

Route files (`page.tsx`, `layout.tsx`) are the exception: they default-export a function as Next.js expects.

- Name components (and their folders) after what they show or do, usually matching their heading or `aria-label` (`ProductReviews`, `PricingPlans`, `UserAvatar`). Never use layout or position words (`HomeRow`, `TopSection`, `LeftColumn`) or vague ones (`Wrapper`, `Content`, `Block`). The same goes for data constants and their properties: name them after what the data is (`LINK_GROUPS` with `links`, `PRICING_PLANS`), not how it's laid out (`COLUMNS`, `ROWS`) or a generic word (`ITEMS`, `DATA`).
- **A prop is defaulted or required, nothing in between:** when one value fits every caller, the component applies it as a default and callers never pass it. Once callers need different values, the prop becomes required and every caller writes it, including the ones that want the former default (`type="button"` and `type="submit"` on a `ProductButton`), so a reader always sees which kind it is. An optional prop is only for something that is really absent by default (`disabled`, `className`). The exception is a shared primitive used across the app, such as a loader or spinner: it offers a standard `size` set as an optional prop with a default (the size its callers use today), so a caller can pick a size without changing the component.
- **Only used variants:** a union of options (a component's `variant`, a `size`) lists only the values some caller passes today. Add a value when the first caller needs it, and remove one when its last caller goes away. The exception is a standard complete set, which stays whole even when part of it is unused: heading levels `h1`–`h4` in a type scale, or the sizes an API documents (`'L' | 'M' | 'S'`), or a shared primitive's standard size set (`'large' | 'medium' | 'small'`).
- Modal visibility lives in the parent: `const [xModalVisible, setXModalVisible] = useState(false)` with `showXModal` / `hideXModal` callbacks.
- Multi-step flows = separate modals per step, wired with `onNextClick` / `onBackClick` from the parent.
- Render optional JSX with `&&` (`{product.badge && <Badge … />}`), not a ternary ending in `: null`; use a ternary only when both branches render something. Coerce a number on the left (`products.length > 0 &&`) so `0` isn't rendered.
- Prefer a named boolean (`const hasResults = …`) over complex inline conditions, in JSX and in `if` statements alike: a condition that calls a function (especially an awaited one) or combines several checks goes into a variable first (`const isPasswordCorrect = user !== undefined && (await verifyPassword(…))`, then `if (!user || !isPasswordCorrect)`); inline single-use expressions and single-use class strings; use a `*_CLASS_NAME` constant only when reused in the file.
- A component renders once per list: when the same component shows one fixed item and then a mapped list (an "All" tab before the category tabs), put the fixed item into the array with the others and map them all, rather than writing the component once by hand and again in the `map`.
- Use concise `map((x) => (<…/>))` unless logic precedes the return. Array callbacks (`map`, `filter`, `find`…) take the whole item, named as the singular of the array (`products.map((product) => …)`, then `product.name`), and never destructure it in the parameter (`({ name, price }) =>`).
- List keys come from the data (`key={item.id}`), never from class names or array indexes. Map over the data itself, not over a styling array.
- Reuse types via indexed access (`GetUserResponse['roles']`) rather than new aliases. A component that shows one item of typed data takes it as one prop named after what the item is, never after the component (`product: Product` on `ProductCard`, not `productCard`), and reads its fields from it (`product.name`): the parent passes the whole item (`<ProductCard isSelected={…} key={product.id} product={product} />`), never spreads it (`{...product}`) and never copies its fields into `Props` one by one (`name: string; price: number`). Spreading is only for a wrapper passing its element's props through (see **Wrapper props**). An item type shared by several components is its own interface (`Product`, with `products: Product[]`). The whole item goes only to a component that represents it (its card, tile or row) and uses most of its fields. A component that needs only a few values from an item for its own job (a list that runs a search with a category's query and sort, a selected state from an id) takes just those values, one prop each, typed by indexed access (`query: Category['query']`, `selectedId?: Product['id']`), and the parent passes each one (`<ProductList query={category.query} sort={category.sort} />`). Name such a prop after what it is in the component, adding the item's name only when the value belongs to something other than the component (`categoryName` on a modal about one product).
- Verify exported names (constants, helpers, response shapes) before using them — don't guess.

## Styling

Tailwind v4 — config lives in the global stylesheet's `@theme`, no tailwind.config. Keep the design tokens (colors, then type) together at the top of `@theme`. Don't mix anything else in with them: other values such as `--shadow-*` and `--container-*` go at the end of the block, after a blank line. The project's tokens are listed in `CLAUDE.md`; prefer them over Tailwind's default palette.

- **Font:** one font from `next/font`, applied once via its `className` on `<html>` in `layout.tsx` — never set a font family on components.
- **Typography:** use `<Typography variant="…">` from `@/components/Typography` — it renders the matching element and `text-<variant>` utility, and makes headings bold. Each `--text-<variant>` token is a px size with its own line height (`--text-<variant>--line-height`). Use these tokens instead of arbitrary font sizes. `variant` decides the element; to change its size or weight, add a utility in `className` — there is no `component` prop. Use `!` exactly when the class overrides a property the variant already sets: every size (`<Typography className="text-h4!" variant="h2">`) and a heading's weight (`font-medium!` on an `h2`). Then always use it, even where the override seems to work without it: Tailwind v4 breaks ties between same-property utilities by class name order, so a plain override wins only by accident, and renaming or adding a token can silently flip it. Where nothing competes, `!` does nothing, so leave it out (`font-semibold` on a `body` or `caption`, which set no weight). Don't add tailwind-merge for this. All text goes through Typography, never bare `span`/`p` (not even as empty or decorative boxes: use `div`); inline text inside a paragraph or button uses `variant="caption"` (a `span`) with a size override.
- **Buttons:** every button is `<Button variant="…">` from `@/components/Button`, never a bare `<button>`. The variant owns the look, and Button adds the shared classes (radius), a default size (height, horizontal padding and text size; the values are in the project's `CLAUDE.md`), `whitespace-nowrap` (a fixed-height button holds one line; a wrapped label overflows it and shifts its baseline). The caller passes layout, the sizes that differ from the default as `!` overrides (`h-[32px]! text-subtitle!`, by the same `!` rule as Typography), and extras that only its placement needs and the variant doesn't set (`shadow-raised` on a button that sits on a card). It never re-adds or changes the colors, borders or radius the variant owns: a new look shared by several buttons becomes a new variant in Button. Button is a Client Component; its props extend the `button` element's (see **Wrapper props**), with `type` narrowed and required (`type="button"` or `type="submit"`, always written by the caller). A clickable button is `type="button"` and passes `onClick`: a `useCallback` handler in a `'use client'` component. A form's submit button is `type="submit"`, usually with no `onClick` (the form's `action` does the work), and Button disables itself and shows `Loader` while the action is pending, so callers pass nothing for it. A Server Component (static or async data-fetching) can't pass functions, so its button becomes a client child under its `components/` folder (see **Server first**): `SubscribeButton`, or `ProductCardButton` taking server-rendered `children`.
- **Links:** every link is `<Link variant="…" href={…}>` from `@/components/Link`, never a bare `next/link`, including a logo link or a link inside a paragraph. The variant owns the look: a text variant (an underlined link in a paragraph), a plain variant for a link whose content gives its look (a logo), and button-look variants for a link that looks like a button. Link writes the button-look classes itself to match Button's. A link is never named or built as a button: what it does decides the element, and a look shared with Button is copied into Link's variants, not imported from a shared file. As with Button, the caller passes only layout and `!` size overrides.
- **Wrapper props:** a shared component that wraps one HTML element or library component and adds a look to it (Typography, Button, Link) extends that element's or component's props, adds only its own (`variant`), destructures only what it uses or changes (`className`, `variant`) and spreads the rest onto the element: a caller can pass any of its attributes or options (`aria-label`, `title`, `prefetch`) without the wrapper listing them one by one. Use `React.ComponentProps<'button'>` for one element, `React.HTMLAttributes<HTMLElement>` when the element varies (Typography), and `React.ComponentProps<typeof NextLink>` for a library component. A prop the wrapper also sets merges with the caller's instead of being overwritten (a submit button's `disabled` while pending). A component that composes several elements (a text field with its label and error) keeps its own explicit `Props`.
- **Cursor:** Tailwind's Preflight gives buttons `cursor: default`, so the global stylesheet restores `cursor: pointer` once, in `@layer base`, for every enabled `button` and `[role='button']`. That covers buttons a library renders too. Never add `cursor-pointer` to a button or `cursor-default` for its disabled state.
- **Shadows:** only `--shadow-*` tokens, never an arbitrary `shadow-[…]`: add a token instead.
- **Layout widths:** a large width that sizes a layout (a standalone form or message page, a sidebar, a modal), shared by several pages or components for the same kind of layout, is a `--container-*` token, used through Tailwind's width utilities (`--container-standalone-page: 400px` → `max-w-standalone-page`, and `w-*`, `min-w-*` or `basis-*` the same way), so changing the token once changes every place. Tokenize it as soon as a second place repeats it, and name the token after the layout it sizes, never after its value or a size word (`standalone-page`, not `400` or `narrow`). A width only one component uses, or a match that's only a coincidence (two unrelated boxes that happen to be 400px), stays an arbitrary value. Small sizes (icons, buttons, inputs) and spacing (padding, gaps) aren't layout widths: they stay arbitrary px values.
- **Values that depend on another component:** a value computed from another component's size (a sticky header's height, used as the scroll margin of the sections a link jumps to) is a `@theme` token named after what it does (`--spacing-header-offset` → `scroll-mt-header-offset`), never an arbitrary value in the component that uses it, where nobody changing the other component would find it. The project's `CLAUDE.md` lists it with what it's computed from.
- Check tokens before using arbitrary values; add a token when a value is semantic or repeated 3+ times.
- **Images:** size `next/image` with classes, not `width`/`height` props. Put the size classes on the image itself and let its parent follow its content (`<Image className="size-[40px]" src={logo} … />` from a static import). Only a remote image, which has no intrinsic size, takes `fill` and `sizes` inside a positioned parent that holds the size classes. `alt` always describes the image (for example the product name), never `""`, even when text beside it repeats the name (a logo next to the site name gets `alt="Acme logo"`). Remote image hosts must be in `images.remotePatterns` in `next.config.ts`.
- Use the simplest classes that give the result: a fixed size (`w-[120px] shrink-0`) rather than `calc()` formulas repeated per breakpoint, or `min-w-*` on items that never grow. Let a box's height come from its content plus padding (`p-[24px_8px]`) rather than an arbitrary `h-*`/`min-h-*`. Never size both a box and the content that already gives it that size (an `h-*` on a link around a sized logo): the content decides, and the box follows. To make a container taller or shorter (a header, a bar), change its top and bottom padding, never a child's size or margin. A box whose children can't size it (only absolutely positioned layers) takes a fixed size. Buttons are the exception: they take a fixed `h-*` so same-size buttons stay equal without tuning vertical padding in each caller. Add responsive variants only when the design needs them.
- No defensive classes: every class must visibly change the result with the content the component actually renders. Don't add `min-w-0`, `shrink-0`, `whitespace-nowrap`, `text-balance`, `w-full`, `justify-*` and similar "just in case". Add one when real content needs it (a long unbreakable string, a scroll row of fixed-width items). If removing a class changes nothing in the browser at any width, delete it.
- Arbitrary pixel values are the norm for spacing and sizes (`mb-[24px]`, `p-[24px_32px]`, `size-[18px]`, `max-w-[340px]`). Always `px`, never `ch`, `em` or `rem` (no `max-w-[18ch]`); `%` only for proportions such as a flex basis. No negative spacing values. Shorthands take 2 or 4 values, never 3 (`p-[0_20px_20px_20px]`, not `p-[0_20px_20px]`), and never override a shorthand with a side class (`p-[4px] pr-0`): write the 4-value form instead. Opposite sides get equal padding (`p-[24px]`, `p-[24px_16px]`), so the 4-value form appears only where the design really needs unequal sides.
- Conditional classes via `clsx`, imported by name: `import { clsx } from 'clsx'`. Argument order: variable class names first (`SIZE_CLASS_NAMES[size]`, a `className` prop), then the static class string, then conditional objects (`{ 'opacity-50': disabled }`).
- Elements:
  - Landmarks: `<main>` (rendered once in `layout.tsx` around `{children}`, so pages never add their own), `<header>`, `<nav>` (`aria-label` when there is more than one), `<footer>`, `<aside>` (sidebars like filters), `<search>` (wraps a search form).
  - Always the real element when it does something or gives structure: `button`, `a`/`Link`, `form`/`label`/`input`/`select`/`textarea`, `fieldset`/`legend`, `h1`–`h6` in order (one `h1` per page), `img` with `alt`, `table`/`th` (data only), `dialog`, `details`/`summary`. Optional: `time`, `blockquote`, `figure`/`figcaption`.
  - `ul`/`ol`/`li` only where it's really necessary: a set of items of the same kind, usually mapped from data, where hearing "list, N items" helps (blog posts, cards, tiles, nav and footer link groups). Everything else is `div`s, including a couple of unrelated controls such as Log In / Sign Up. A component rendered once per list item returns the `li` itself as its root, with the item's own width and layout classes, so the parent maps it straight inside the `ul` (`{products.map((product) => <ProductCard {...product} key={product.id} />)}`), never wrapping it in an `li`. The exception is a client component (a button): its `li` stays in the server parent (see **Server first**). A bulleted list of facts in prose is `<ul className="mb-[24px] flex list-disc flex-col gap-[12px] pl-[24px]">` / `<li>`.
  - `dl`/`dt`/`dd` for name–value pairs that describe one subject (product specs, stats, a product's key features), so screen readers tie each value to its name. Separate items that each have a title and a description (cards, posts) stay a `ul`. Wrap each pair in a `div` (`key` from the data) for layout. `dt` always comes before `dd` in the markup: when the value shows first (a stat number above its label), reverse it visually with `flex-col-reverse`. A reversed column packs its content to the bottom, so when pairs of different heights share a row, add `items-start` on the parent to keep them top-aligned.
  - Every component returns a semantic root element, never a bare `div` or a fragment (route files may return a fragment). The exception is a component that is just a layout group with no fitting element (a pair of buttons), which uses a `div`. A page block is `<section aria-labelledby="…">` pointing at its heading's `id` (Typography takes `id`), with the id in a `const TITLE_ID = '…-title'` used in both places; a block without its own heading uses `aria-label`.
  - `div` only for layout inside those elements, and only when an existing element can't take the layout itself. Before wrapping children in a `div`, put the classes on their parent instead (`flex flex-col justify-center` on the card rather than an inner `div` to stack its texts, the parent's padding rather than a `div` with a margin). No `<article>`.
- Vertical margins flow top to bottom: each element sets `mb-*` for the gap below it; never `mt-*` or `my-*`. The one exception is an optical alignment nudge: a column whose smaller text should line up with a larger heading beside it moves down with `mt-*`, never `pt-*`. Add a nudge only when the element visibly misaligns without it, never by default or copied from another site, and never to change its container's height. The gap at the top of a container is its own top padding. The gap below a component goes on its root element, never on its last child. The last element in a container gets no bottom margin: the space below it is the container's bottom padding.
- **Consistency:** the same relationship always gets the same styling across the codebase: spacing, sizes, widths, colors, radius, type, scrollbars. Before picking a value, find how existing components handle the same case and reuse it; never introduce a one-off value. If the right value differs from an existing one, change it everywhere. Spacing between texts follows the project's text spacing scale in `CLAUDE.md` (measure the visible gap, including a scroll row's shadow padding).
- **No repeated layout fixes:** when several components need the same layout fix (page width `mx-auto max-w-[…]`, a shared inset), put it once in the shared parent, usually `layout.tsx`, instead of repeating it in each component.
- Space between sibling elements is `gap` on their flex container, never padding on one of the siblings. Repeated siblings (mapped list items, wrapping columns) always get one `gap` on the parent (`flex flex-col gap-[12px]`), never `mb-*` on each child with `last:mb-0`. `mb-*` in plain block flow is only for a few distinct stacked elements (a heading, then a paragraph), which don't need a flex+gap wrapper: never make a container `flex flex-col` or `grid` only to space a few distinct children (a card's title and description, a form's fields and its button), give each one its `mb-*` instead. A `gap` column is for mapped siblings and for a group whose last child is conditional (fields followed by an optional error message), where margins would need `last:mb-0` or a conditional class. Padding is only for the inset between a box and its own content. Prefer plain `gap-[…]`, as the rest of the codebase does, even in a wrapping row where wrapped items then get the same gap. Use `gap-x-*`/`gap-y-*` only when the design really needs different gaps on the two axes.
- Layout with flexbox; use grid only when flex can't do it simply: genuinely two-dimensional layouts, such as N equal columns that wrap into rows, which flex could only do with a `calc()` basis that repeats the gap (`basis-[calc((100%-12px)/2)]`, use `grid grid-cols-2` instead). Absolute positioning only for overlays/floating decorations.
- z-index values are consecutive integers (`z-1`, `z-2`, `z-3`), one per stacking layer, never large or arbitrary numbers (`z-10`, `z-50`, `z-[999]`). A new layer takes the next number, or goes between existing ones and the numbers above it shift up. The current order is listed in `CLAUDE.md`; keep it up to date.

## Implementing designs

- Match the design exactly (size, spacing, colors, type, radius, shadows); never guess values.
- Icons: use the real exported SVG (kebab-case file name) rendered with `next/image` or `<img alt="…" />`. Never placeholders, emoji, or icon libraries (lucide, react-icons).

## Adding rules

When the user asks for a new rule or points out something that should be one:

1. **Generalize it:** write the principle behind the case ("no defensive classes", not "don't use `min-w-0` in the stats card"), with the reason when it isn't obvious.
2. **Place it** by asking whether it would still make sense in a different project:
   - Yes → this file, with a neutral example (`ProductCard`, never a component name from the current project).
   - No, it's about this project (a color, its API, its z-index order) → `CLAUDE.md`.
   - Both (a general rule with project values, like a spacing scale) → the rule here, the values in `CLAUDE.md`.
   - Unclear (a decision such as "light theme only") → ask "this project only, or all projects?" before writing it.
   - Never in Claude's memory: memory is per project and doesn't travel. It holds only facts about the user or project that no file records.
3. **Check existing rules:** extend a rule it overlaps instead of adding a near-copy; if it contradicts one, ask which wins.
4. **Apply it:** find code that already breaks the new rule and fix it.
5. **Enforce it:** add a lint rule only when the user asks for one; don't suggest one with every new rule.
6. **Report** in the reply which file the rule went into, so the user can correct the placement.
